# v0.18.0 릴리즈 수동 복구 회고

[2026-10-30 릴리즈](https://github.com/dnotitia/reef/releases/tag/v0.18.0)는
배포와 관계 데이터 검증까지 완료했다. 이 문서는 배포 중 필요했던 수동 작업,
확인한 원인, 배포 도구의 변경 범위를 기록한다. 원본 행·문서 백업과 상세 운영
기록은 비공개 릴리즈 아티팩트에 보관한다.

## 수동 복구가 필요했던 지점

| 관찰한 문제 | 당시 작업 | 재발 방지 |
| --- | --- | --- |
| 관계 ID 배열에 문서 URI, 존재하지 않는 ID, 다른 워크스페이스 참조가 섞여 있었다. 첫 오류만 확인할 수 있었다. | 실제 대상을 확인해 URI를 ID로 바꾸고, 해석할 수 없는 참조는 원본을 보존해 별도 참조로 정리했다. | 롤아웃 요청 전에 모든 대상의 참조 오류를 모은다. 영수증에 이슈 ID·필드·배열 위치·오류 종류를 기록하고, 저장된 URI와 정확히 일치하면 교정할 ID를 제시한다. |
| AKB 요청이 오래 대기하고 API 준비 상태가 흔들렸다. | 요청 시간 제한과 동시성 제한을 적용했다. API Pod 교체도 했지만 증상이 다시 나타났다. | 데이터 읽기는 20초, 문서 PATCH는 120초로 제한한다. 워크스페이스 작업을 두 개씩 실행하고, 알려진 일시적 전송 오류만 최대 세 번 시도한다. |
| 재시도마다 이미 반영한 문서도 다시 써서 리비전과 파생 작업이 늘어났다. | 완료 작업을 별도 파일에 보존하고 원본 문서의 관계 필드와 커밋을 대조해 재쓰기를 줄였다. | PATCH 응답을 문서별 체크포인트로 원자적으로 저장한다. 같은 문서 커밋과 같은 목표 관계는 검증 단계로 바로 넘어간다. |
| 문서 쓰기는 끝났는데 공개 그래프가 늦게 반영됐다. 기존 검증 대기는 10초였다. | 운영자가 배포된 AKB 작업기 구현을 추가 프로세스로 임시 실행해 대기열을 처리하고 그래프를 다시 읽었다. | 전체 대상의 쓰기를 먼저 마친다. 그래프 검증은 기본 30분 동안 읽기로 대기하며 진행 상태를 출력한다. 시간 초과 후에는 같은 영수증으로 `repair`를 실행한다. |
| 같은 워크스페이스의 명시적 AKB 관계가 Reef 행과 다르면 검증이 끝나지 않았다. | 기존 명시적 의존관계 하나를 일반 참조로 옮기는 우회를 했다. | 소유권 판정을 고쳤다. 명시적 AKB 관계는 독립된 사용자 데이터로 유지한다. 필수 관계의 존재와 문서가 만드는 암시적 관계의 초과 여부를 검증한다. |
| 이전 버전의 Evicted Pod가 남아 정상 배포를 실패로 판정했다. | 종료된 과거 Pod만 확인해 삭제했다. | `Failed`·`Succeeded` Pod와 삭제 중인 Pod를 현재 런타임 검증에서 제외한다. 실제 실행 중인 Pod의 이미지·준비 상태 검사는 유지한다. |
| 작업 중 생성된 이슈 때문에 검증 시점의 개수가 영수증 개수와 달랐다. | 새 이슈를 포함한 원본과 공개 그래프를 추가 검증했다. | 영수증 개수는 검증 시점의 스냅샷으로 다룬다. 검증 중 원본이 바뀌면 새 스냅샷을 읽고 변경된 문서만 처리한다. |

API 준비 상태 변동의 근본 원인이 모두 밝혀진 것은 아니다. Pod 교체를 영구적인
해결로 간주하지 않는다. 그래프 지연은 별도로 확인했다. 당시 AKB 작업 루프는
임베딩 배치마다 Native 파생 변경을 한 건씩 처리해 관계 갱신이 누적됐다.
AKB의 작업기 처리량과 연결 풀 진단은 AKB 운영 측의 책임으로 남는다.

## 개선한 배포 흐름

1. 이미지와 릴리즈 좌표를 영수증에 기록한다.
2. 기존 활성 설치 목록을 고정하고, 모든 대상의 쓰기 권한·행 관계·문서를 사전 검사한다.
3. 사전 검사가 통과하면 AKB 롤아웃을 요청한다. 적용된 대상이 고정한 목록과 같은지 확인한다.
4. 두 런타임을 배포하고 준비 상태와 불변 이미지 좌표를 확인한다.
5. 관리 지침 갱신을 마치고, 모든 워크스페이스의 문서 쓰기를 진행한다.
6. 문서마다 쓰기 전후 원본을 확인하고 `expected_commit`으로 조건부 PATCH한다.
   성공 응답의 커밋과 목표 관계를 영수증 옆 체크포인트 디렉터리에 저장한다.
7. 공개 그래프를 검증한다. 행 스냅샷이나 문서 커밋이 바뀌면 해당 투영을 다시 확인한다.
8. 전체 설치 목록을 다시 대조한 뒤에만 `deployed`로 기록한다.

각 단계는 성공한 대상과 실패한 대상을 개별 저장한다. 실패한 대상의 마지막
문서 쓰기 이후에도 성공한 대상의 영수증은 남는다. 파일이 없거나 손상된
체크포인트는 저장소 복구가 필요한 오류로 보고한다.

## 실패 후 재개

영수증 파일과 `<receipt>.relations/` 디렉터리를 함께 보관한다. 영수증마다
CLI 프로세스를 하나씩 실행한다. 롤아웃과 런타임이 준비된 상태라면 다음과 같이
관계 복구만 재개한다.

```bash
AKB_BACKEND_URL=https://akb.example.com \
REEF_CONTROL_PLANE_TOKEN="$REEF_CONTROL_PLANE_TOKEN" \
NAMESPACE=my-namespace \
REEF_RELATION_VERIFY_TIMEOUT_MS=1800000 \
  deploy/k8s/deploy.sh repair --receipt /secure/reef-release.json
```

`repair`는 영수증의 불변 Manifest와 적용된 롤아웃을 확인하고 두 런타임의 실제
이미지·환경·준비 상태를 읽는다. 이후 남은 관계 복구를 수행한다. 새 이미지 빌드,
릴리즈 등록, AKB 롤아웃 변경, Kubernetes 적용은 이 명령의 작업에 포함되지 않는다.
운영 도구의 체크아웃과 수리 대상 릴리즈의 소스가 달라도 영수증 좌표로 검증한다.

- AKB 롤아웃이 아직 막혀 있으면 원인을 해결한 뒤 `resume`을 사용한다.
- 런타임 준비가 끝나지 않았으면 `deploy`로 배포를 완료한다.
- `failure.code=invalid_relations`이면 표시된 행과 필드의 의미를 확인해 데이터를
  교정한다. 존재하지 않는 이슈나 다른 워크스페이스의 참조에는 운영자의 판단이 필요하다.
- `failure.code=projection_pending`이면 원본 쓰기가 이미 끝났을 수 있다.
  AKB의 파생 작업 상태를 확인하고 같은 영수증으로 `repair`한다.
- `failure.code=checkpoint_error`이면 함께 보관한 체크포인트를 복원한다.
  저장된 쓰기 응답을 확인할 수 있어야 재쓰기 없이 재개할 수 있다.

새 체크포인트가 없는 문서는 현재 원본과 문서 커밋으로 조건부 쓰기를 수행하고
그 응답부터 기록한다. 문서의 현재 관계 필드를 직접 읽을 공개 API가 없는 상황에서
공개 그래프만 보고 원본 필드까지 올바르다고 추정하지 않는다.

## 일반 릴리즈 절차와 구분할 항목

- 운영 overlay의 CPU·메모리·SSO·SSE 설정 준비는 일반 배포 절차다. `repair`는
  런타임을 읽어서 확인하므로 이 설정을 다시 적용하지 않는다.
- 이미지의 버전·커밋 별칭과 GitHub Release 발행은 별도 릴리즈 절차다. 빌드
  명령은 기존 별칭을 보존하고 고유 빌드 태그와 digest를 산출한다.
- App Credential은 앱 토큰으로 교환해 사용한다. 설치 조회 권한만 있는
  워크스페이스는 실행용 앱 inventory와 관리자 inventory가 다를 수 있다.
  릴리즈 대상 비교에는 관리자 inventory를 사용한다.
- 배포 후 릴리즈·스프린트 마감은 [릴리즈 정책](release-policy.md)의 PM 절차다.
